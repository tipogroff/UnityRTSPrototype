## Compatibility evaluation

### 1) Environment version compatibility

- Current project strategy targets fixed compatibility (v0.6.1-style 27-channel line) and explicitly avoids assuming `master` compatibility.
- MicroRTS-Py README deprecation notes confirm observation-channel drift across versions.
- Therefore, any external checkpoint without explicit version binding is high risk.

Result: not validated for canonical use.

### 2) Observation/action compatibility

- Existing project contract expects Unity-side canonical mapping and Week 5 adapter path.
- External checkpoints referenced in docs are demonstrated mostly on 16x16 evaluation/training setups and may carry different assumptions.
- Without direct shape/mask head verification and adapter test pass, compatibility remains unproven.

Result: not validated for canonical use.

### 3) Checkpoint format / architecture transparency

- Scripts clearly support `.pt` state dict loading.
- But a specific externally hosted candidate with complete architecture + env metadata package was not confirmed in this selection pass.

Result: insufficient transparency for immediate canonical selection.

### 4) Operational feasibility

- There is no local ready-made file to run Day 5 meaningful batch immediately.
- Current pipeline can run with random fallback, but this is infrastructure-only by contract.

Result: external ready-made is not operationally ready in this workspace now.

## Fallback strategy

If a ready-made external teacher appears later, it can only replace the selected path after passing all gates:

1. Version gate
- Explicitly pinned MicroRTS/Gym version and map/task profile must match our canonical assumptions.

2. Contract gate
- Observation/action/mask compatibility must be verified with a short operational validation run.

3. Transparency gate
- Architecture + checkpoint metadata must be documented.

4. Feasibility gate
- Checkpoint must be actually accessible and loadable in current environment.

Until then:
- Keep `trainable_teacher` as selected source.

## Minimal practical next step (own teacher training)

Goal:
- Produce first meaningful teacher checkpoint (not random) with minimal scope.

Recommended entrypoint:
- `experiments/ppo_gridnet.py` in a fixed MicroRTS-Py environment version aligned with canonical stack.

Minimal plan:

1. Freeze environment
- Use pinned MicroRTS-Py version (project-preferred fixed line), fixed Python and package versions.

2. Run short deterministic teacher training smoke
- One seed first, short horizon, save checkpoint.

3. Validate checkpoint load
- Load in eval script once and confirm no shape/action-head load mismatch.

4. Feed checkpoint into existing Week 5 exporter
- Replace random fallback with canonical checkpoint and collect a small meaningful batch.

Example command template (adjust inside pinned MicroRTS env):

```bash
cd experiments
python ppo_gridnet.py \
  --total-timesteps 10000000 \
  --num-bot-envs 24 \
  --num-selfplay-envs 0 \
  --partial-obs False \
  --seed 1
```

Then point Week 5 rollout runner to produced checkpoint:

```bash
python python/week5_teacher/run_teacher_rollout.py \
  --policy-path <PATH_TO_TRAINED_CHECKPOINT> \
  --policy-algorithm ppo \
  --checkpoint-env-version <PINNED_ENV_VERSION> \
  --episodes 1 \
  --batch-mode debug
```

Note:
- This is a minimal operational step only, not a full Week 6 training framework.
